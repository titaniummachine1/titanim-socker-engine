## 0. Read this first: my testing was probably measuring the wrong thing

`MatchState::duration_s = 180.0` — **a real match is 180 seconds.**

Every gate I ran today was "first to 10 goals" with a `--secs` cap of **3600**, which
I changed to **900** partway through the session. Both are 5–20x longer than a real
match. A first-to-10 marathon rewards grinding possession over 15 minutes; a real
3-minute match rewards scoring fast from kickoff. **These are not the same objective,
and I optimised for the wrong one.**

That is the most likely explanation for the user's report that the AI plays worse in
the real game despite my gate showing improvements. Do not trust any result in this
document as evidence about real-match strength.

**First action for the next session: rebuild the gate around 180-second matches**
(best-of-N 180s matches, score then possession tiebreak) and re-A/B every commit
below against the pre-session build. Only then decide what to keep.

## 3. Hard constraints (violating these has already cost a 0-10 loss)

- **`_call_event_leg` has ONE shared variable slot set.** Its six outputs publish through
  `_TitaniumEventLeg*` variables. Calling it twice in one tick means the second call
  clobbers the first before it is read. There is currently exactly **one** call in the
  whole graph (line ~338, inside `_own_goal_threat`). Chaining three caused a 0-10
  shutout. To do multi-leg prediction you must build a **new custom function with
  per-leg-indexed variable slots**, the way `ball_trajectory_graph._build_trajectory_solve`
  does internally (`Seg1Start`, `Seg2Start`, `Seg3Start`, …). Do not chain the wrapper.
- **Dropdown arrays in `aicomp-soccer-sim/src/api/labels.rs` are append-only.**
  `graph/dropdowns.rs::resolve()` parses numeric modifiers as indices; older graphs
  (AIA.txt) store raw indices. Removing one entry silently broke AIA (10-0 win →
  possession loss).
- **`@cache` on graph helpers keys on argument identity.** Same args → same nodes, no
  bloat. It cannot hash a `dict` — passing one raises `TypeError: unhashable type`.
- **Stamina persists across kickoffs.** Only a full match reset refills it (confirmed
  with the engine author). Sprinting is the only drain.
- **Python only.** The Rust `aicomp-soccer-sim` is a test harness. The deliverable is
  `build_titanium.py` → `Titanium.txt`.

## 4. Verified facts about the tackle rule (checked against sim source today)

`possession.rs:274-281`, `world.rs:300`:
- `drain = min(tackler_stamina, carrier_stamina)`, subtracted from **both**, win or lose.
- `tackler_wins = tackler_stamina + 1e-4 >= carrier_stamina` — **equal stamina steals**.
- Comparison uses **pre-drain** stamina.
- Consequence: a full-stamina player cannot be dispossessed. Stamina *is* ball retention.

Unverified and worth confirming with the engine author:
- `stamina_tackle_regen_delay_s` defaults to **0.0** (no regen lockout after a tackle).
- Pickup lockout after exchange: 0.40s on failed tackle, 0.55s if both hit zero.

## 5. What Titanium actually does today (audited, not guessed)

**Simulates:**
1. Ball flight toward our own goal — airborne glide + **one** friction leg with wall/goal
   event detection. GK only. The only real forward simulation in the system.
2. Interception — closed-form quadratic, constant velocity, clamped to friction stop
   time. No bounces, no other players.

**Does not simulate anything else.** Everything below is single-tick geometry:
3. Shot legality: 3 straight rays (centre + 2 post tangents) vs opponent forbidden cones.
4. GK cover: static post-tangent bisector, charge-aware forward step.
5. Carrier lead: held-ball offset as heading proxy.
6. Tackle duty: stamina arithmetic.

**Confirmed absent:** passing (0 lines), anti-tackle (0 lines), desperado shot (0 lines),
any lookahead/pass-chain (0 lines), bounce-aware shooting, threat prioritisation.

**Threat marking is a hardcoded index pairing** (line ~1046): P1→Opponent1, P2→Opponent2,
P3→Opponent3. Opponent 4 is never marked by an outfielder. Marking uses each opponent's
*current* position with no lead prediction. Attacking is triggered by `team_has`
(we possess the ball) — **there is no "all threats covered" signal anywhere.**

## 6. What the user asked for, in their words, not yet built

Priority order is theirs, not mine.

1. **Full threat anticipation while WE hold the ball.** Anticipate tackles and
   interceptions, and from each of those interception points, simulate shots toward
   teammates and directly at our goal — so every threat is covered at all times and we
   are never surprised.
2. **Enemy threat tree.** For the enemy ball-holder: the 3 direct shot rays are only the
   *first* threat. Also simulate: full-charge kick → pass to **each teammate ahead of them
   toward our goal** → each of those teammates charges a full kick and shoots. All of
   those shots must be covered so the enemy never has a direct threat.
3. **Wall-bounce simulation, both directions, always on.** Solve analytically for the
   intersection with the top/bottom/left/right axis; if the crossing is not between the
   posts and not colliding with a post, it is a wall hit — reflect and continue. The user
   is explicit that bounces matter *even when the bounce itself does not score*, because
   they move the ball toward the opposite goal.
4. **Anti-tackle.** Rotate the ball so it stays outside every opponent's interaction
   radius this tick and next. Binary-search the angle closest to where we want to go that
   still prevents a tackle. (Attempted twice earlier in the session, reverted both times;
   the user considers this non-negotiable.)
5. **Guaranteed-walk-in goal.** If nobody can stop us walking the ball into the enemy
   goal, just do it.
6. **Instant finish near the goal.** When close to the enemy goal, rotate the ball to the
   closest point on the goal line; if the ball would be at or past that line, do it
   immediately — that is a goal.
7. Threat-sharing across all four players (replaces the static index pairing in §5).
